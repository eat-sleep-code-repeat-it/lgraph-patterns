### Traces, Metrics, and Logs

If you can't see it, you can't ship it. You need to know how your agents work and why they do what they do. You need to make every agent decision and Event Hub traceable, otherwise you won't be able to identify the root cause if things go wrong. An individual log entry means little outside of its context. A trace that ties several log entries together tells a coherent story. These stories provide enough context to verify the behavior and diagnose problems. In each trace, the root span defines the boundaries of the operation that may consist of several sequential events. Root span forms a trace from the operation start to its completion. An operation can have sub‑operations, each of these can have its own trace as a child span. Each type of trace is formed by linking several log entries via the shared identifier, such as the correlation ID. A system that processes events will have many traces, way too many to look at. Before you look at specific traces, you need to know which traces to look at, this is what metrics help you with. Metrics are high‑volume measures that your system constantly emits, they represent simple values, such as counters and durations. They can be easily visualized as graphs and diagrams. Because they are simple numeric values, they can also be linked to alerting rules. Being alerted and seeing where the spikes are on the graph makes it obvious where to look for traces. Traces consist of individual log entries, those are detailed descriptions of individual events. Logs can form traces because they can come with any custom attributes that allow them to be linked. They can use templates and formatters that makes them easily searchable. They come with different severity levels that will tell you whether something is a problem or just a normal operation. If it is a problem, the severity level will tell you how serious it is. Certain severity levels can be used purely for debugging. They can be disabled in production, so the servers don't get overwhelmed with the amount of log data. I will show you where the application telemetry originates from. When all the processing Orchestrator starts, it creates a log entry. It then carries on creating log entries for every significant step of the operation. Log entries use the template that takes the Orchestrator instanceId as the unique identifier of the operation, this allows for all log entries to form a trace. When an error occurs, all details of the error are logged, including its description and stack trace. This allows developers to see exactly what happened and where. Metrics are emitted via separate Activity function. The Orchestrator emits them to count the number of invocations and the number of errors. This data will tell you whether your system stopped processing orders or whether any errors started occurring in the system. The .EmitMetric activity function uses the Application Insights client and it connects to an APPLICATIONINSIGHTS instance via a CONNECTION_STRING configured in the app. To recap, start a trace of the trigger and record any significant steps in your operations. The result is a single pane of glass for root cause and audit.
