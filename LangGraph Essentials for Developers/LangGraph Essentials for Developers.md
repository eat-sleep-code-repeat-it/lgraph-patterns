Introduction to LangGraph and Its Core Components
Welcome to LangGraph Essentials for Developers. In this course, we'll learn the foundations of building agentic workflows using LangGraph. My name is Deepali Srivastava, and I'll be guiding you through each concept as we move from basics to hands‑on implementation. So let's get started. First, let's see what LangGraph is. LangGraph is an orchestration framework, which means that it helps you manage how different components in an AI system work together. It gives structure and control to your agentic applications, and saves you from writing a lot of new code that you would otherwise have to write in plain Python. LangGraph is built by the LangChain team, so it integrates well with LangChain abstractions, like models, prompts and tools, but it can also be used without LangChain. In this course, we'll use these familiar LangChain abstractions inside our LangGraph workflows. LangGraph works through graph‑based workflows. This design helps you visualize how your system behaves and controls the flow of logic. Now let's see the main components of LangGraph. As the name LangGraph suggests, the graph forms the core of the framework, it visually represents your entire workflow. It is made up of different nodes that are connected by edges. Each node represents a specific task within the workflow, and each edge is a connection between two nodes, it indicates the flow of control. Next, we have state, which is the central data structure that is shared by all the nodes of the graph, it acts as the memory of your workflow. Let's take a closer look at what it is. State stores all the important data that your workflow needs, like inputs, intermediate results, and final outputs. It is usually defined as a class using either TypeDict or Pydantic. This keeps your data well structured and type safe. All nodes in the graph have access to this shared state, they can read from it and update it. Each node receives the current state, performs some computations, and returns an update to the state. So as your workflow progresses, the state evolves by capturing updates from each node, and this is how information flows between different steps of your workflow.
Steps to Build and Run a LangGraph Workflow
Let us now look at how a LangGraph application is built. It's a three‑phase process. In the first phase, we build the graph. We start by defining the structure of state, we'll then identify the specific steps of our workflow, and define different nodes for these steps. Each node will be implemented as a Python function. We then initialize a new graph structure by creating an instance of the class StateGraph, this will manage all the nodes and the edges. After that, we add each node in the graph, and define an entry point, which is the node where the execution should start, and then we add edges to connect nodes according to our workflow logic. After all the nodes and edges are defined, we will compile the graph structure and prepare it for execution. Finally, we'll execute the compiled graph by passing in the initial state, and we'll receive the final state as a result. Now let's see how all this is implemented in code. To add nodes, we call the add_node method. It takes two arguments, first is the name that you assign to the node, and second is the function that should run when that node is activated. Next, we add edges using the add_edge method, it connects two nodes by using their names. These node names are the same names that we had specified in the add_node method. Understanding Persistence in LangGraph
In this module, we'll see how LangGraph adds persistence to workflows so that they can remember past executions and survive crashes. We'll start by understanding what persistence is and how it is implemented. We know that state is the memory of the workflow. But by default, this state is ephemeral, it exists only while the workflow is running. Once the execution of the workflow ends, the state is lost. If you invoke the graph again, it starts with a fresh state. LangGraph provides a built‑in mechanism for saving the state of the workflow so that it can be restored later, it is called persistence. So, persistence is the ability to save the state and reload it later. Persistence allows a workflow to pick up exactly where it left off. If the system crashes, restarts, or we intentionally pause the execution, then the progress is not lost, the workflow can simply continue from the last saved point. Due to the persistence layer, LangGraph can support several powerful capabilities. For example, chatbots can remember the full conversation history instead of only the latest message. It also allows multiple independent conversations to run without interfering with each other. Some workflows can run for hours or even for days. With persistence, we don't have to keep everything in memory all the time, the workflow state can be saved and loaded again whenever needed. Persistence helps in implementing human‑in‑the‑loop workflows, where a human can review or edit the state after pausing the execution, and then the workflow can continue by incorporating the human feedback. Another feature enabled by persistence is the ability to go back to an earlier saved point and explore a different execution path, this is called time travel. If a workflow run crashes midway, we can simply continue from the most recently‑saved state, instead of starting over from the beginning. So, persistence makes the agent workflows reliable, resumable, and easier to understand and debug.

HITL: Concepts and Use Cases
So far, we have made workflows that would execute from start to end without any human involvement. This approach is powerful, but it can be risky sometimes. To make reliable and safe applications, we can incorporate human feedback at some critical points in the workflow. Streaming Basics
In this module, we'll cover streaming execution in LangGraph and also build an interactive web user interface. Let's start by understanding why streaming matters and how it is different from the way we've been executing our graphs so far. Until now we've been using invoke to execute LangGraph workflows. The invoke method runs the entire graph and returns the final state only after all the nodes have finished executing. In real‑world applications, this can lead to a poor user experience, as the users may have to wait for a long time without seeing any progress or some partial output. To solve this problem, LangGraph supports streaming execution. Streaming exposes the intermediate progress of the graph, and so we can see the execution step by step as it happens. Invoke treats the execution like a black box. Input goes in and final output comes out, while streaming opens the box and shows how the graph is executing internally. This is especially useful in long‑running workflows, where waiting for a single final result is not practical. Streaming is also used for interactive and user‑facing applications, because it allows users to see the intermediate outputs in real time. In LLM‑based applications, latency can be significant, and streaming can help in improving the user experience. Streaming can also be used for debugging and observability, as you can track how the graph executes step by step. Now let's see how we can implement streaming. LangGraph provides a method named stream for streaming the execution. This method can be called in the same way as we call the invoke method. We pass the initial state and also config dictionary if required. The difference is that the invoke method gives a final result, while the stream method returns a generator. This generator yields chunks of data as the graph executes. We can iterate over this generator to get those chunks of data. The stream method is synchronous. LangGraph also provides a non‑blocking, asynchronous version called astream, which works the same way. So everything that works with stream also works with astream, but it allows applications to continue running while waiting for results. Now that we understand how streaming works, let's look at the different streaming modes that LangGraph supports. These modes control how much detail is emitted during the execution. In the values mode, LangGraph streams the complete workflow state after every step, and this can be useful when you want a full snapshot of how the state evolves over time. Next is updates mode. It streams only the changes made at each step, instead of streaming the entire state. The debug mode provides low‑level execution details, like the step numbers, node start and completion, and internal metadata. This mode is especially useful for debugging and for understanding how the graph behaves internally. The messages mode streams message chunks along with metadata. This mode lets you see the LLM's response appear gradually, just like live typing in a chat application. You can choose the right mode, depending on what information you want to observe. If you don't specify a stream mode, LangGraph uses the graph's default stream mode, which is the updates mode.

Offline Evaluation
In this lecture, we'll see how to conduct offline evaluations in LangSmith. Offline evaluation is the process of testing your application before it reaches the user. It ensures that any changes that are made in the application improve its performance. To conduct offline evaluations, the first thing that you need is high quality data, against which you can test your application. In LangSmith, you can create datasets. A dataset is a structured collection of examples where each example contains inputs and the corresponding reference outputs used for evaluation. These are often called golden datasets because they contain perfect reference outputs that represent the ideal behavior which you expect from your application. Examples can be added to datasets in different ways. You can add examples by typing the inputs and the reference outputs. You can also generate data synthetically using an LLM. This allows you to quickly create a large number of examples based on existing patterns. You can also add data from existing project traces. This helps you build datasets from real user interactions. Datasets can also be created programmatically using automated rules. After you've created your evaluation dataset with golden examples, the next step is to run experiments. An experiment is the process of running a specific version of your application over a dataset. When an experiment is executed, LangSmith runs your application on every example in the dataset, and it measures how well the outputs match the perfect reference outputs present in the dataset. To measure the success of your experiments, you need a way to score the outputs, and this is done using evaluators. An evaluator is a function used in an experiment to measure a specific quality of the output. It grades the experiment's output against the reference output in your dataset. You can specify multiple evaluators for your experiment. Some common evaluators are correctness, which checks whether the response is factually accurate, relevance that checks whether the output actually answers the question or conciseness that checks whether the response is brief. Evaluators can be implemented in two different ways. The first type uses custom code where you define clear rules to measure the outputs. For example, in the conciseness evaluator, you can check the length of the response. So these evaluators are used to check metrics that have clear and fixed answers. Open‑ended criteria like correctness or relevance do not have a fixed answer, and so simple code logic is not sufficient. They require reasoning, and for that, we can use LLM‑as‑a‑judge. In this approach, the LLM will compare the output with the reference output using a rubric, and it will produce an evaluation score. Once the evaluators are defined, you can use them in experiments to test and compare different versions of your application. This helps you observe how any changes to prompts, models or logic affect the performance, and this way you can choose the best version before deployment.
