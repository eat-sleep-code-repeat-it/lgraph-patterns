###Identity and Access

Your agents perform business‑critical tasks, therefore you shouldn't allow just anyone to trigger your agents. Users of services that are allowed to trigger them need to prove that they are who they claim to be and that they are allowed to perform the actions they are trying to do. This is where authentication and authorization come in. Authentication forces the users and agents to prove they are who they claim to be. A common example of authentication is username and password. The idea is that the password is secret and only the real user knows it. By providing the password, the user says, it's really me. However, even if your identity is proven, it doesn't mean you are allowed to access certain restricted areas. This is where authorization comes in, it ensures that whoever is trying to perform the action is allowed to do so, it's like only admin users are allowed to access admin‑only areas. There are multiple ways of enabling both authentication and authorization. In Azure, each service can be given a managed identity, other services can be explicitly configured to accept or deny access from this service. No explicit secrets are stored, it's configured at the level of each individual Azure resource. In device‑to‑device communication, mutual TLS is often used, for example, it's very common in MQTT protocol commonly used in the Internet of Things. Each device has a valid X.509 certificate. The certificate key is validated on the server, this is how the server knows it's dealing with a genuine device that is supposed to be part of its network. For authorization, one of the most common ways of enforcing permissions is via role‑based access control. Roles define who is allowed to do what. Every individual user or agent can have multiple roles combined together, this allows for fine‑grained access control, where specific resource and operations can be restricted by specific roles. Roles can be assigned or revoked at any time. Resources can also be secured via a private endpoint, this endpoint would only be accessible inside a private network and be completely invisible and inaccessible to the public. Only services running inside the private network can see it, however, in some cases, external services can connect to it via an encrypted tunnel, such as VPN. Let's look at some examples of enforcing security in Azure. Many Azure services, including Azure Functions apps, have the Identity blade inside these settings, this is where a managed identity can be assigned to this service. The managed identity can then have roles assigned that would grant it access to specific areas of your Azure subscription. I can then open another resource and see if this managed identity has access to it. For example, I may want to Function app to send events to a specific Event Hub's instance, in this case, I will select the Event Hub instance I'm interested in. Once in, I can check what resources have what access. If I don't see any appropriate roles for the selected user or managed identity, I can grant it. To recap, entities that trigger your agents need to prove their identity. Modest identities remove the need to store secrets. Role‑based access control gives you the fine‑grain control. Tie access to the smallest surface and keep traffic private.
