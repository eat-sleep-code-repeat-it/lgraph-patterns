
Data Security and Privacy
Securing access to your data is important. However, it's equally as important to ensure that you don't accidentally leak sensitive data to the outside, this is what data security is all about. The first principle is to make sure that you never post raw, Personal Identifiable Information, PII, such as names, addresses, phone numbers, etc., in places where it's not relevant, such as application logs. If it comes as part of loggable payload, redact it so it's not visible. Not sure what information is classed as PII? Assume that any using information is. Use whitelist to explicitly allow certain safe information to be published. When any sensitive data is being transferred, encrypt the payload. Don't transfer raw data as is, ensure that any encryption keys are stored securely, revoked when compromised, and rotated and refreshed when needed. Ensure that access tokens don't live longer than they are needed, sometimes their life span should be long, but most of the time it shouldn't be. I will show you how PII can be redacted. I have enhanced the login in the order‑processing saga so not only I can know that an order has been processed, but also who processed it. This helps me to narrow down the problems if they ever occur in the application. Now, I need to make sure that the sensitive PII never reaches the logs, for this purpose, I added a couple of helper functions to replace raw names, emails, payment card information, and addresses with redacted values. For example, the system will only log the email domain and not the whole email, likewise for payment card, it will only log the last four digits. Here's the recap, redact before your store, encrypt across boundaries, and treat model tool tokens like production secrets, scoped, rotated, and watched.
